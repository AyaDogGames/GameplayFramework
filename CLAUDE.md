# CLAUDE.md — GameplayFramework plugin (canonical agent guide)

This is the canonical guide for AI agents and contributors working in this repository. `AGENTS.md` is a short pointer to this file; `README.md` is the human-facing setup guide. When this file disagrees with prose elsewhere, re-open the cited source and trust the code.

## What this is

`GameplayFramework` is an **Unreal Engine 5.8** C++ plugin for building fully replicated, **data-driven Gameplay Ability System (GAS)** games. Almost everything is wired up through GameplayTags, Data Assets, and Data Tables; core classes are meant to be subclassed in C++ or Blueprints. Prefix conventions: `Da` (GameplayFramework module), `CE` (Collectibles module); `U`=UObject/component, `A`=Actor, `F`=struct, `I`=interface.

## Critical: this is a SHARED plugin (one checkout in a `SharedPlugins/` container)

- This plugin is its **own git repo** (`https://github.com/AyaDogGames/GameplayFramework.git`,
  formerly `ModularGameplayFramework` — GitHub redirects the old URL), checked out at
  `C:/Source/SharedPlugins/GameplayFramework`.
- Consumer projects (GlitchShaper, CollectorsEdition, Glitchwalker) do **not** vendor, submodule,
  or symlink it. Each consumer's `.uproject` declares
  `"AdditionalPluginDirectories": [ "../SharedPlugins" ]` — the engine scans the *children* of
  that container for `.uplugin` files. There is **no `Plugins/GameplayFramework`** inside any
  consumer repo; each consumer's `setup.sh` clones this repo into the container if missing.
- **There is exactly one copy on disk — editing it affects every consumer.** Commit plugin
  changes in this repo, on this repo's branches; after any plugin change, rebuild all consumer
  projects before committing on their side.

## Modules (all Runtime — there is NO editor module)

From `GameplayFramework.uplugin`:

- **`GameplayFramework`** — `Type: Runtime`, `LoadingPhase: Default`. The main module. Startup (`Private/GameplayFramework.cpp`) just declares the `DA_GameplayFramework` log category and logs a load message — **no asset-type or factory registration**.
- **`Collectibles`** — `Type: Runtime`, `LoadingPhase: PostDefault`. Depends on the `GameplayFramework` module. Startup logs "Collectibles submodule Loaded." (a verbatim UE-*module* log string — not a git submodule).
- **`DaProcGen`** — `Type: Runtime`, `LoadingPhase: Default`. Seeded procedural placement (M4). Declares its own `DA_ProcGen` log category. Holds `FDaDungeonLayout` (engine-math-only seeded room/corridor/wall generator — see below) and `UDaProcGenLibrary` (its Blueprint/Python surface). This is the module that brings the **PCG** plugin dependency in for every consumer.

There is **NO `GameplayFrameworkEditor` module** and no editor target of any kind. `GameplayFrameworkEditorToolingPlan.md` is an **aspirational design proposal**; its `UDaProjectSetupWizard` / `EGameType` / factories exist only in that markdown, not in code.

## Source map (`Source/`)

`Public/` holds headers; `Private/` mirrors it with implementations.

- **`AbilitySystem/`** — `UDaAbilitySystemComponent`, `UDaAbilitySystemLibrary`, `UDaAbilitySet : UPrimaryDataAsset`. `Abilities/`: `UDaGameplayAbilityBase`, `UDaGameplayAbility_BaseTriggeredInputAction`, `UDaGameplayAbility_Death`, `UDaGameplayAbility_Projectile`, `UDaGameplayAbility_ToggleUILayer` (push a widget class onto a `UI.Layer.*` stack, or pop it if this ability already pushed it — `InstancedPerActor` so it can remember, `LocalOnly` because opening a menu is not the server's business, and it optionally shows the mouse cursor while open and restores it on close; it exists so a UI toggle needs no new input plumbing at all: an InputAction, an IMC key, an input-config pair and an ability-set grant, exactly like every other button), and the look/move input abilities `UUDaGameplayAbility_LookAction` / `UUDaGameplayAbility_MoveAction` (the literal **double-`U`** prefix is real — in both type name and filename; do not "fix" it). `Effects/`: `UDaGameplayEffect_DealDamage`, `UDaGameplayEffect_HealToMax`, and the condition penalty pair `UDaGameplayEffect_ConditionWorn` / `UDaGameplayEffect_ConditionCritical` (infinite duration, granting `Item.Condition.Worn` / `.Critical` and no magnitudes — games add the real penalties in content). Both configure their granted tags in `PostInitProperties`, **not** the constructor: `FindOrAddComponent` is the only public door to `GEComponents` and it `NewObject`s with an empty name, which is fatal while `IsInConstructor` — do not "simplify" that back into the constructor. `Modifiers/`: `UDaMMC_Health`. `Tasks/`: `UDaAbilityTask_TargetDataUnderCursor`.
- **`AbilitySystem/Attributes/`** — `UDaBaseAttributeSet` (carries a `SetIdentifierTag`; subclasses map tags->attributes via `TagsToAttributes` in their constructor); `UDaCharacterAttributeSet` (Health/Mana), `UDaCombatAttributeSet` (damage/healing meta), `UDaDynamicAttributeSet`; `UDaExecution_HealWithMana`; data assets `UDaAttributeInfo`, `UDaAttributeSetDataAsset`.
- **`AI/`** — `ADaAICharacter : ADaCharacterBase`; `ADAAICharacter_NPC : ACharacter, IAbilitySystemInterface` (dialog NPC, **not** a `ADaCharacterBase`); `ADaAIController`; BT services `UDaBTService_CheckAttackRange`, `UDaBTService_CheckLowHealth`; BT tasks `UDaBTTask_DoAbilityToSelf`, `UDaBTTask_DoAbilityToTargetActor`; `UDaNPCDialogData`.
- **`Inventory/`** — the **`FFastArraySerializer` system** (nine files in each of Public/Private): `UDaInventoryComponent` (server-authoritative; replicates a `FDaInventoryList`, `MaxSlots=20`, `InventoryTags`; `AddItem`/`RemoveItem`/`MoveItem`/`UseItem`/`DropItem`/`SaveInventory`/`LoadInventory`, static `GetInventoryFromActor`; `OnEntryAdded`/`Removed`/`Changed` + `OnItemUsed`/`OnItemDropped` delegates; `Server_*` RPCs + `Internal_AddItem`; delegates broadcast on authority AND from FastArray client callbacks — mutate only via the BlueprintCallable API). `UseItem` sends an `Action.UseItem` gameplay event to the owner's ASC (OptionalObject=definition, EventMagnitude=slot) and consumes when `bConsumeOnUse`; `DropItem` spawns the definition's `PickupActorClass` (default `ADaItemActor`) in front of the pawn. `FDaInventoryEntry : FFastArraySerializerItem`, `FDaInventoryList : FFastArraySerializer`, `UDaItemDefinition : UPrimaryDataAsset` (`GetPrimaryAssetId()` -> type `"ItemDefinition"`; fields: DisplayName/Description/Icon/DisplayMesh/ItemTags/MaxStackCount/`AbilitySetToGrant`/`bConsumeOnUse`/`PickupActorClass`/`EquipSlotTags`), `IDaInventoryItemInterface` (`GetItemDefinitionID`/`GetStackCount`/`AddToInventory`), `UDaMasterInventory` (empty Blueprintable subclass). **UI adapter layer** (also under `Inventory/`, recreated as thin view-models over the FastArray — NOT replicated): `UDaInventoryItemBase` (`CreateFromEntry`), `UDaStackableInventoryItem`, `UDaInventoryUIWidget` (`IUserObjectListEntry` list-entry widget), `UDaInventoryWidgetController` (binds entry delegates, rebuilds view-model array, `UseItem`/`DropItem` pass-throughs, plus `AssignToHotbarSlot(FGuid, 1..4)` / `ClearHotbarSlot(1..4)` — loadout writes against `Equip.Slot.ItemN`, which are ASSIGNMENTS and not equips — and `GetInventoryComponent()` so a widget can reach the loadout and `OnLoadoutChanged` without resolving the component itself); `UDaInventoryComponent::GetItems()` is the BlueprintPure BP-compat bridge returning those view-models — prefer the widget controller for new work. The view-model surfaces **per-instance** state as well as the definition's: `StatCounts` (every `Item.Stat.*` leaf as tag->count, with `GetStatCount`), `bUsesCondition`/`Grade`/`Condition`/`ConditionCap`/`ConditionBand`/`GetConditionFraction`, and `bIsEquippable`/`EquipSlotTags` — all copies taken in `CreateFromEntry`, banded through the one `ComputeConditionBand`, so a widget can draw a worn sword differently from a mint one without re-resolving anything. `ConditionBand` is meaningless unless `bUsesCondition`; check it first. The old UObject-based inventory factory and blueprint library were **deleted and not recreated** (the equipment component was later rebuilt on the same FastArray pattern — see **`Equipment/`** below). Entries also carry **per-instance identity**: `StatTags` (`TArray<FDaTagStack>`, tag->count, mirrored into a per-entry accelerator map) reachable through `SetItemStat`/`AddItemStat` (delta form; the client sends the delta and the server does the read-modify-write via `Server_AddItemStat`)/`GetItemStat` plus `FindEntryByItemID(FGuid)` — the identity lookup the equipment side and the stat API both go through — a deterministic `GetItemSeed(ItemID)` derived from the entry GUID, and the replicated+saved **loadout** (`TArray<FDaLoadoutEntry>` of slot tag -> ItemID) behind `SetLoadoutSlot`/`GetLoadoutItemID`/`GetLoadout` — the loadout lives here, on the PlayerState's inventory, so it outlives any pawn. Loadout changes are notified through the **parameterless** `OnLoadoutChanged`, broadcast on the authority from `Internal_SetLoadoutSlot`/`ClearLoadoutForItem` (real changes only — clearing an already-empty slot is accepted and silent) and on every client from `OnRep_Loadout`. Parameterless on purpose: replication hands the OnRep the array after the fact, so a payload would either need a shadow copy to diff against or would differ between the server and client paths, and a delegate whose payload depends on where it fired is worse than none. Listeners re-read `GetLoadout`/`GetLoadoutItemID`. `ADaItemActor::Interact` adds the actor's `ItemDefinitionID` to the interactor's inventory when valid (no-op with a log warning otherwise) — except for an actor a player DROPPED: `Internal_DropItem` hands the removed entry to `ADaItemActor::InitializeDroppedItem(const FDaInventoryEntry&, UStaticMesh*)`, which keeps it in a plain non-replicated `DroppedEntrySnapshot` (server-only by design), and the pickup then goes through `UDaInventoryComponent::RestoreEntry(const FDaInventoryEntry&)` so the ItemID, StatTags, tags and AbilitySetID come back verbatim in the entry's original slot. The snapshot is SPENT on the first successful restore (and the actor disables its collision and refuses further `AddToInventory` calls): `Destroy()` only marks the actor for end-of-frame teardown, so without that a second interact in the same frame — the same player double-tapping, or a second player racing the first — would fall through to the `AddItem` fallback and mint a free pristine duplicate. Partial-stack drops deliberately carry no snapshot (the identity stays with the entry left behind), and `RestoreEntry` refuses an ItemID the inventory already holds. **Condition** rides the same StatTags: `UDaItemDefinition::ConditionConfig` (`FDaConditionConfig`: `bUsesCondition`, `DefaultGrade`, `DecayPerUse`, `CapBase`/`CapPerGrade` behind `GetConditionCap(Grade)`, `WornThresholdPct`/`CriticalThresholdPct`, `WornEffect`/`CriticalEffect`, `RepairCreditsPerPoint`/`RepairGradeCostScale`) opts an item in; `Internal_AddItem` stamps `Item.Stat.Grade` and fills `Item.Stat.Condition` to the cap on acquisition — onto the LOCAL entry, before it is published, so the added-broadcast is coherent instead of showing a condition-user at 0 for an instant. `RestoreEntry` deliberately does NOT (a drop snapshot carries its own stats; re-initialising would be a free repair on drop→re-pickup). `LoadInventory` DOES, but only as a migration: an entry whose definition uses condition and which carries no `Item.Stat.Condition` at all — a save written before that item type opted in — is filled to its grade cap on the way in, because a stat count of 0 is indistinguishable from "absent" and would otherwise read as Broken and refuse to equip forever. Client-originated stat writes are additionally filtered: `Server_SetItemStat`/`Server_AddItemStat` reject a protected leaf through `IsClientWritableStat` (currently `Item.Stat.Grade`, which fixes both the cap and the repair price); authority-side callers use the direct wrappers and are unaffected. `UDaItemDefinition::IsDataValid` errors on the two condition misconfigurations that produce unusable items: a grade cap of 0, and `bUsesCondition` with `MaxStackCount > 1`. `RepairItem(FGuid, int32 Points = 0)` is the credits sink (`Points = 0` buys as much as the purse allows): authority-validated, priced in double precision with a thousandth-of-a-credit slack so a float curve cannot overcharge by one, clamped to what is actually missing, charged through `ADaPlayerState::AdjustCredits` on the resolved owner PlayerState, with `GetRepairCost`/`GetMissingCondition` as the BlueprintPure quotes a shop UI prices from (they work on a client, off replicated state).
- **`Equipment/`** — applied-equipment mirror of the inventory FastArray, on the **pawn**: `UDaEquipmentManagerComponent : UActorComponent` (server-authoritative, replicates a `FDaEquipmentList`; `EquipItem(FGuid, FGameplayTag SlotTag)`/`UnequipSlot(SlotTag)` route through `Server_*` RPCs to `Internal_*`, `ApplyLoadout()` re-equips everything the owner's inventory loadout names, `GetEquippedItemID`/`IsItemEquipped`/`GetItemIDForAbility`, static `GetEquipmentFromActor`, `OnEquipped`/`OnUnequipped` delegates). Equipping validates against the definition's `EquipSlotTags`, spawns and attaches the definition's `ActorsToSpawn` (class + socket + relative transform), and grants its `AbilitySetToGrant` (or the entry's `AbilitySetID` override) to the owner's ASC; unequipping destroys the actors and takes the grants back. `FDaAppliedEquipmentEntry : FFastArraySerializerItem` (ItemID/ItemDefinitionID/SlotTag/SpawnedActors + `UPROPERTY(NotReplicated) GrantedHandles`), `FDaEquipmentList : FFastArraySerializer` (client callbacks re-broadcast the delegates only — cosmetic actors are spawned on the authority and replicate to clients, so equipment actor Blueprints must have **Replicates** set). The loadout itself is NOT here: it is on the inventory component (above), which is why it survives respawn and save/load. Coherence and lifetime rules the component enforces on the authority: it binds the resolved inventory's `OnEntryRemoved` (in `BeginPlay`, retried from `ApplyLoadout` because the PlayerState arrives with possession) and unequips any slot holding an item that left the inventory, while the inventory clears loadout assignments naming that item — so a dropped or consumed item cannot stay equipped or assigned; `UnequipAll()` drains every slot and is called from `ADaCharacter::UnPossessed` (with `EndPlay` as a backstop) because the ASC lives on the PlayerState and a corpse that kept its grants would double-grant the respawned pawn's re-applied loadout; `OnUnequipped` broadcasts BEFORE teardown so host listeners see live actors and grants, matching client `PreReplicatedRemove` timing, and `OnEquipmentChanged` fires from `PostReplicatedChange` so clients hear about `SpawnedActors` references that only resolve in a later delta. Hotbar activation is `UDaGameplayAbility_QuickSlot` (file under `AbilitySystem/Abilities/`): grant one per button with InputTag `Input.Item1..4` and `QuickSlotTag` = `Equip.Slot.Item1..4`. The decision itself — Use a consumable, equip-toggle an equippable — lives in `static UDaEquipmentManagerComponent::ActivateItemSlotForPawn(APawn*, FGameplayTag)` so the ability (authority side) and `UDaHotbarWidget`'s slot click (client side, through the existing `Server_*` forwarding) run the same code and cannot drift. `static GetItemSlotTag(1..4)` is the one place hotbar slot NUMBERS become `Equip.Slot.ItemN` TAGS. The **mechanical** end of the condition system lives here too, all authority-only: `EnsureAbilityDecayBinding` binds the resolved ASC's `AbilityActivatedCallbacks` (ability **activation**, deliberately not `AbilityCommittedCallbacks` — committing is per-ability opt-in and Blueprint abilities authored without a Commit node never do it, so a commit binding would silently never decay most content), and `OnAbilityActivated` maps the spec handle back through `GetItemIDForAbility` to subtract `DecayPerUse` from that instance's `Item.Stat.Condition`; the inventory's `OnEntryChanged` drives `RefreshConditionPenalty`, which bands the item (`ComputeConditionBand`: integer percent of the cap, thresholds are strictly-below, 0 is Broken; the `EDaConditionBand` enum itself lives in the tiny `Public/Inventory/DaConditionBand.h` and is a `UENUM(BlueprintType)`, so read-only consumers — the UI view-model, a shop widget, the debug overlay — get the enum without this component's replication machinery, while this stays the only function that decides which band a number falls into) and keeps ONE penalty GE handle per SLOT, swapping effects only on a band crossing; Broken unequips the slot — but on the NEXT TICK, via `HandleDeferredBreak`, never inline: the decay that breaks an item arrives from `OnAbilityActivated`, which runs inside the ability's `PreActivate`, and the actor `Internal_UnequipSlot` destroys is that still-activating ability's `SourceObject`. The deferred handler re-checks the band before tearing anything down, because a repair may have landed in between. The loadout assignment is left alone either way (a repaired item is one hotbar press from being back), and `Internal_EquipItem` refuses a condition-user at 0 outright. `ClearConditionPenalty` resolves the ASC BEFORE dropping the handle and keeps the handle (with a warning) when it cannot, so an infinite-duration penalty can never be stranded un-removable. The inventory and ASC bindings are compare-and-rebind rather than bind-once, and `ReleaseOwnerBindings()` (called from `ADaCharacter::UnPossessed`) gives the ASC callback back, because the ASC lives on the PlayerState and a re-possessed pawn must not wear down the outgoing player's items. Both `Internal_EquipItem` and `Internal_UnequipSlot` open with a GUARDED authority check (`LOG_WARNING` + `return false`), not a hard `check()`: a `Server_*` body really can execute on a non-authority — every UFunction called from editor Python does, because `FEditorScriptExecutionGuard` forces `FunctionCallspace::Local` — and the assert those two used to carry took the whole editor down when it happened (measured: `unequip_slot` on a client's manager). Because of the same mechanism, the `EquipItem`/`UnequipSlot` return value off the authority is an OPTIMISTIC true that says nothing about the outcome and can mask an RPC that never left the caller; read the replicated equipment state instead. Full context: `C:/Source/GlitchShaper/docs/roadmap/STATE.yaml` (unit V6 notes) and `C:/Source/GlitchShaper/docs/roadmap/M2-REVIEW-FIXES.md`. `UDaConditionComponent` (also under `Equipment/`) is the **cosmetic** end of the condition system: put it on an item's visual actor and it pushes the material-parameter contract `Da_Wear_Intensity` / `Da_Wear_Seed` / `Da_Wear_Grade` into MIDs on the owner's mesh components, refreshing from the inventory's `OnEntryChanged` (so it works on clients with no RPCs of its own and replicates nothing). It identifies its item through `UDaEquipmentManagerComponent::FindItemIDForSpawnedActor` — or is told, through `SetItemID(ItemID)` (the item is looked up in the wearer's inventory) or `SetItem(Inventory, ItemID)` (caller supplies the inventory too, for visuals nobody equips). A third route skips resolution entirely: `SetExplicitWear(Intensity, Seed, Grade)` pushes numbers the caller already has and stops the resolve retry — that is how a DROPPED `ADaItemActor` looks as worn as the item that was dropped, since its inventory entry no longer exists for anything to look up. Materials implementing none of the three parameters are left untouched. Full contract: **`docs/ConditionMaterialContract.md`**.

  **Hotbar and inventory panel** (`UI/DaHotbarWidget.{h,cpp}`, `UI/DaInventoryPanelWidget.{h,cpp}`) — theme-neutral C++ bases, both **Blueprintable and both able to build their own default widget tree**, so a bare BP subclass with nothing authored in the designer still renders something real instead of an empty rectangle. That is the whole shape of the contract: subclass in UMG and author visuals (bind `SlotRow` / `RowContainer`, drive the display from `OnHotbarRefreshed` / `OnPanelRefreshed` and the BlueprintPure queries), or subclass and author nothing and take the plain default.
  `UDaHotbarWidget : UUserWidget` is a row over `Equip.Slot.Item1..N` (`SlotCount`, 1..4). It resolves the LOCAL player's loadout (the PlayerState's inventory) and equipped state (the pawn's equipment manager) itself, and refreshes from their delegates — `OnLoadoutChanged` for assignment, `OnEntryAdded/Changed/Removed` for stack count and condition, `OnEquipped`/`OnUnequipped` for the highlight — all of which fire on clients too, so a client's row shows the CLIENT's own loadout. Bindings are **compare-and-rebind** on a 0.25s timer, not bind-once: the PlayerState arrives after the widget on a client and the pawn is a new actor after every respawn. `OnUnequipped` gets its own handler because it fires BEFORE teardown (deliberately, to match client `PreReplicatedRemove` timing) — a plain refresh from there is told, correctly and uselessly, that the departing item is still equipped, so the leaving slot/item pair is masked out for that one refresh. Every slot's cached state is exposed as `FDaHotbarSlotState` through `GetSlotState`/`IsSlotAssigned`/`IsSlotEquipped`/`GetSlotItemID`/`GetSlotConditionFraction`/`GetSlotStackCount`/`SlotHasIcon`: those read the CACHE, not the live inventory, on purpose, so a test asking "does the row show this?" gets the answer the row drew rather than a fresh read that would paper over a refresh it never received. `ActivateSlot(1..4)` is the click, and it calls `UDaEquipmentManagerComponent::ActivateItemSlotForPawn` — the quick-slot ability's own function.
  `UDaInventoryPanelWidget : UDaUserWidgetBase` (so it is a `UCommonActivatableWidget`, pushed and popped on a layer by `UDaGameplayAbility_ToggleUILayer`) lists one `UDaInventoryRowWidget` per entry: name, stack count, condition when the item has one, and per-row `[1][2][3][4]` hotbar-assign buttons routed through `UDaInventoryWidgetController::AssignToHotbarSlot`. It feeds itself — it creates its own `UDaInventoryWidgetController` over the local PlayerState's inventory when nothing handed it one — so the panel and the hotbar read the same view-models and cannot describe one item two ways. Per-row buttons rather than "select a row, then press a number key": the number keys are already the hotbar's own buttons, and this panel deliberately keeps game input live (`GameAndMenu` + `NoCapture`) so the key that opened it can close it. Rows are also selectable (click the name) with `AssignSelectedToSlot` for a themed subclass that wants that instead. `static GetActivePanel(WorldContextObject)` finds the constructed panel in a given world — a static registry, because an ability instance is not reachable from outside the ASC and a multi-window PIE session has one panel per world.
  `ADaHUD` puts the hotbar up: `HotbarWidgetClass` (unset = no hotbar, which is how projects without one stay untouched) + `InitHotbar`/`RemoveHotbar`/`GetHotbarWidget`. It is added to the **player screen** at `HotbarZOrder`, not pushed onto the `UI.Layer.Game` stack — an activatable-widget stack shows only its top entry, so the hotbar and the overlay would hide each other — and it goes up from **`InitRootLayout`**, not `InitOverlay`: a GlitchShaper network client reaches the former and never the latter, and hooking the hotbar to `InitOverlay` left every client without a row (measured). The only `UMVVMViewModelBase` in the plugin is the Collectibles `UCECollectibleViewModel` — there is **no** inventory ViewModel. Also here, and the one place the plugin uses **raw Slate**: the **item debug overlay** (`UI/DaItemDebugOverlay.{h,cpp}`), a `SNew`-built panel with no UMG asset and no theme behind it, toggled by the `Da.Debug.Items` console command (`FAutoConsoleCommandWithWorld`, so it acts on the world it was typed in — one overlay per game viewport, which is what lets a multi-window PIE session inspect the host in one window and a client in another). It lists the local `ADaPlayerState`'s credits and one row per inventory entry (definition, Grade, Condition/cap, band via the now-public `UDaEquipmentManagerComponent::ComputeConditionBand`, equipped slot, stack) and carries cheat buttons for wear / break / repair / equip / unequip / drop / +100 credits. It refreshes by polling every 0.25s rather than binding delegates (a debug tool that misses a redraw is a nuisance; one holding a stale binding to a respawned pawn is a crash) and adds **no RPC surface**: every button calls the same BlueprintCallable component API a game UI would, so pressing one in a client window really exercises the client→server RPC path. The `SDaItemDebugOverlay` widget is `.cpp`-local (this module's Slate dependencies are private); the public header holds only `UDaItemDebugLibrary` — `ToggleItemDebugOverlay` / `IsItemDebugOverlayVisible` / `GetItemDebugOverlayRowCount`, the last two so an automated smoke can assert the overlay resolved a real inventory. The whole thing compiles out of shipping (`#if !UE_BUILD_SHIPPING`); the console command and the library stay, and report "not visible".

## Gameplay tags (native)

Declared with `DA_DECLARE_GAMEPLAY_TAG_EXTERN` / `CE_DECLARE_GAMEPLAY_TAG_EXTERN` and defined with `UE_DEFINE_GAMEPLAY_TAG[_COMMENT]`.

- **Core** (`CoreGameplayTags.{h,cpp}`, namespace `CoreGameplayTags`): roots include `Input`, `Character`, `AbilitySet`, `Attributes`, `Inventory`, `InventoryItem`, `Message`, `UI`, `Status`, `Action`, `Pickup`, `Level`, `Ability`, `Event`, `Gameplay`, `Cheat`, plus the item-identity/equipment roots `Item` (`Item.Stat` base, `Item.Stat.Grade`, `Item.Stat.Condition`, and the condition-band tree `Item.Condition` with `.Worn` / `.Critical` — the four M2 tags; `Item.Stat.Durability` was declared in M1 and never used, and M2 retired it) and `Equip` (`Equip.Slot.WeaponMain`, `.WeaponOff`, `.Skill1`, `.Skill2`, `.Item1`..`.Item4` — the hotbar slots).
- **Collectibles** (`CollectiblesGameplayTags.{h,cpp}`, namespace `CollectiblesGameplayTags`): `Collectibles.*` plus extensions of the core trees (`Inventory.Type.Collectibles`, `Attributes.Stats.Collectible*`).

## Conventions

- **Data-driven GAS.** New attributes: subclass `UDaBaseAttributeSet`, set a parent `SetIdentifierTag`, and register attributes in the constructor via `TagsToAttributes.Add(Tag, GetXAttribute)`. `Attributes.Stats.Primary` are set directly; `.Secondary` are derived via gameplay effects.
- **Tag-driven UI (MVC/MVVM).** AttributeSet (model) -> WidgetController (listens/broadcasts) -> UserWidget (view), wired by gameplay tag. Built on CommonUI + ModelViewViewModel.
- **Replication.** Inventory and attributes are server-authoritative; inventory uses `FFastArraySerializer` delta replication. Mutate inventory via the component's BlueprintCallable API (which routes through `Server_*` RPCs), not by editing entries directly.
- **Asset Manager.** `UDaItemDefinition::GetPrimaryAssetId()` returns the `"ItemDefinition"` type, but the plugin does **not** register it at startup and ships no `Config/`. Consumers must add `ItemDefinition` (and any other primary data-asset types they use) to `PrimaryAssetTypesToScan` in their own `DefaultGame.ini`.

## `DaProcGen` — seeded placement (M4)

- **`FDaDungeonLayout::Generate(Seed, FDaDungeonLayoutParams, OutTiles)`** (`Public/DaDungeonLayout.h`) — bounded rejection-sampled non-overlapping room rects (spacing-inflated overlap test) → each room L-corridors to the nearest already-connected room's centre (X leg at the source row, then Y leg at the target column; placement order drives iteration, Manhattan distance breaks toward the lowest index) → 8-neighbour wall rind → room 0's cells become `Entry`. Rooms keep a one-cell margin so the rind always lands inside the grid. Returns **false** only when the attempt budget runs out below `RoomCountMin`, leaving `OutTiles` empty; callers re-roll from a derived seed (`HashCombine(Seed, Attempt)`), bounded, and must treat an empty layout as valid-but-featureless rather than as a crash.
- **Determinism is the product.** One `FRandomStream`, integer draws only, the same draws consumed in the same order on every path, and a final sort by grid coords so the tile **array** — not merely its hash — is a pure function of (Seed, Params). That is what lets a session replicate one int and have every machine build the same dungeon. `FDaLayoutTile::TileSeed` is `HashCombine(GetTypeHash(Grid), RunSeed)`, which is where downstream (PCG) variation must get its randomness from; anything time- or order-dependent breaks the agreement.
- **`FDaDungeonLayout::HashTiles`** — order-independent fingerprint (per-tile integer hash, sorted, folded, seeded with the count). Integer content ONLY: the transform floats are excluded, so `CellSize` moves the geometry without moving the fingerprint and two processes can compare hashes safely. Empty layout hashes to 0.
- **`UDaProcGenLibrary`** (`Public/DaProcGenLibrary.h`) — `GenerateLayoutTiles` / `GetLayoutHash` / `HashLayoutTiles` / `CountTilesOfType`, all `BlueprintCallable` statics. `int64` returns because a `uint32` does not survive a Blueprint int; that is also the surface the consuming project's Python smokes drive.
